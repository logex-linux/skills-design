# Apple Keynote Slide Style

这是一套“观察设计语言、重新创作”的工作流，不是 Apple 官方模板，也不承诺复刻任何具体发布会。目标是借鉴苹果发布会最稳定的设计机制：清晰的叙事、一次只讲一个观点、巨大的可读性、克制的视觉层级、真实体验演示和有节奏的 reveal。默认皮肤采用浅色、冷灰、深色文字和少量柔和彩色流动；深色舞台只有在内容确实需要沉浸、夜景或硬件 reveal 时才启用。

不要直接复制 Apple 标志、事件海报、产品图、界面截图、字体文件、音乐或 keynote 视频。使用用户拥有、明确授权、自己拍摄、自己生成或可公开使用的资产；品牌和产品名称只在事实描述确有必要时出现。

## 何时使用

- 用户想做“像苹果发布会一样”的产品发布或主题演讲；
- 需要把产品功能列表变成电影感的演示叙事；
- 需要从视频中抽取 slide 版式、配色、动效和演讲节奏；
- 需要输出 Keynote、PowerPoint、Figma、HTML 或 Remotion 的实现方案；
- 需要评审一份 deck 是否真的清晰、克制、可读，而不只是“黑底白字”。

## 交付前先定义

先把请求规范化为一张 scene plan，再做视觉设计：

```yaml
audience: 谁在看，以及他们要做什么决定
promise: 演示结束时，听众应该相信或执行的一件事
format: live | silent-video | hybrid
language: zh-CN | en | ...
canvas: 1920x1080
assets: 用户提供 / 授权图库 / 自制 / 生成
output: keynote | pptx | figma | html | remotion | outline
constraints: 时长、屏幕尺寸、品牌色、数据来源、可访问性
```

如果用户没有指定画布，默认 1920×1080、16:9。若是现场演讲，优先保证远距离可读；若是静音视频，所有关键论点必须在画面上成立，不能依赖演讲者补充。

## 核心工作流

### 1. 先做观看与取证，不要先选模板

研究对象按“公开旗舰 keynote”定义：产品发布会、WWDC 主 keynote；不把 Platforms State of the Union、技术 session、产品发布后的新闻稿当作主发布会。研究时间窗默认是滚动 36 个月；需要更换时间窗时，把边界写在研究记录中。

每看一场，建立一张 event card，记录：

```text
event → 日期 / 类型 / 总时长 / 官方视频入口
opening → 开场 30–90 秒的情绪、背景、事件主视觉
chapter → 章节顺序与每段时长
reveal → 第一次出现产品或核心概念的方式
demo → 真实场景、UI、人物、产品特写之间的比例
proof → 数字、对比、规格、合作或可用性信息如何出现
close → 收束画面、CTA、音乐和余韵
palette → 背景、主要文字、事件色、产品色
layout → 中心 / 左右分栏 / 全屏 / 设备 mockup / 数据
motion → 淡入、位移、缩放、遮罩、镜头运动、转场
confidence → official | observed | inferred | uncertain
```

观察视频时不要逐帧复制。每场只截取或记下四类“状态”：开场状态、章节转场、产品 reveal、证明或结尾状态。对本地研究笔记只保存时间码、文字摘要和原创草图；不要保存 Apple 影像文件或把截图作为最终设计资产。

每完成一场，必须把它放进 [slide-atlas-2023-2026.md](references/slide-atlas-2023-2026.md) 的 inventory，而不是只写“浅色 / 深色 / 有渐变”。至少记录：

- 画面状态：空舞台、形体 reveal、真实动作、UI 近景、内容板、满版峰值、行动收束；
- 密度曲线：这一场在哪里留白，在哪里达到视觉峰值；
- 连续 anchor：下一页从上一页继承了什么主体、颜色、边缘、动作或数字；
- 反模式：有没有把内容做成同权重浮卡、让正文躲到主体后面、用装饰光晕冒充证据；
- 证据等级：`observed`、`inferred` 或 `uncertain`。

如果暂时不能访问完整视频，必须明确写出“章节级观察”或“代表帧观察”，不能把推断写成逐帧事实。

### 2. 把功能清单重写成发布会叙事

默认叙事骨架：

```text
人类感受 → 熟悉的摩擦 → 一个承诺 → 视觉 reveal
→ 真实体验 / demo → 证据 → 必要细节 → 邀请行动
```

不是每个 deck 都需要完整八拍，但每一场 scene 只保留一个主张。把“功能 A、功能 B、功能 C”改写成“用户先遇到什么、然后完成什么、最后得到什么”。

每页都用下面的句式自检：

```text
这页要让听众在 3 秒内明白：________。
如果删掉所有正文，只剩标题，标题仍然应该表达：________。
这张图 / 这个数字比一句话更快证明：________。
```

推荐章节顺序：

1. Human hook：一个人、一个瞬间或一种普遍感受；
2. Tension：今天为什么不够好；
3. Promise：新的体验是什么；
4. Reveal：名字、产品、核心概念或关键视觉首次出现；
5. Lived experience：把功能放进真实生活、工作或创作场景；
6. Proof：一项数字、对比、规格或第三方事实；
7. Details：只给完成决策所必需的细节；
8. Invitation：价格、可用时间、CTA 或一句有余韵的结语。

### 3. 为每个 scene 选择最小版式

可复用的 scene 类型：

| 类型 | 目的 | 画面构成 |
| --- | --- | --- |
| Hero title | 建立情绪和主张 | 大标题 + 单一背景或单一主体 |
| Statement | 给出判断 | 一句结论 + 极短解释 |
| Chapter | 重置注意力 | 章节名 + 事件色或抽象形态 |
| Product reveal | 让对象成为主角 | 产品轮廓 / 局部 / 侧面 + 名称 |
| Feature close-up | 证明一个细节 | 一张大图或一个 UI 状态 + 一句好处 |
| Lived demo | 把功能变成体验 | 人物 / 场景 / 设备 + 3 步以内 |
| Stat / proof | 给出可信锚点 | 一个数字 + 单位 + 口径 / 来源 |
| Comparison | 解释提升 | before / after 或两列对比，避免 6 格卡片墙 |
| Spec detail | 完成选择 | 2–4 个必要规格，不做百科全书 |
| Availability | 促进行动 | 日期、价格、版本或 CTA，明确且安静 |
| Close | 留下记忆点 | 重复核心承诺 + 极少量行动信息 |

如果一页同时出现背景、问题、结论和 CTA，拆成至少两页。若标题包含“以及”“同时”“并且”并连接两个独立结论，优先拆页。

### 4. 建立舞台，而不是堆装饰

#### 画布与栅格

- 默认画布：1920×1080；所有尺寸按 `width / 1920` 等比例缩放；
- 左右安全边距至少 80 px，上下至少 100 px；背景可以出血，关键信息不能出血；
- 使用 12 列栅格，左右边距 80 px，列间距 24 px；标题、产品、图表共享同一组导线；
- 使用 8 px spacing scale；大留白是层级工具，不是需要填满的空白；
- 同类 scene 固定标题基线、产品对齐线和底部信息线，章节页才有意改变节奏。

#### 颜色

默认浅色舞台令牌：

```json
{
  "background": "#F4F5F7",
  "surface": "#FFFFFF",
  "surfaceBright": "#F8F9FB",
  "foreground": "#111216",
  "muted": "#686E78",
  "faint": "#9297A1",
  "accent": "#246BFE",
  "positive": "#2CBF8A",
  "warning": "#F2B93B",
  "line": "#D9DCE3"
}
```

不要把“苹果发布会感”简化成黑底蓝字。先从事件主视觉抽象一个颜色关系，再决定是否有充分理由切换舞台：

- 浅色舞台是默认：白 / 冷灰 + 深色字 + 一条低透明度的柔和虹彩流动，适合软件系统、社区、教育和轻盈体验；
- 深色舞台是特例：黑 / 近黑 + 纯白字 + 一种事件色，只在硬件 reveal、夜景、性能和沉浸体验有明确叙事收益时使用；
- 高饱和事件色：只负责章节识别或一次关键强调，不要让每个模块都抢色；
- 同一颜色只承担一种语义；颜色不是唯一的状态或比较信号，必须同时使用文字、数字、形状或位置。

#### 构图密度与反模板规则

近三年的公开视频显示，发布会不是每页都极简，也不是每页都做卡片墙，而是在空舞台、单主体、真实动作、内容板和满版峰值之间切换。执行时：

- 8 页 deck 至少包含 1 页 quiet stage、1 页有主题的 rich content board，以及 1 页明确的 visual peak（可以是满版图像、单一大主体或大尺度 reveal）；这些是画面状态，不要为了达到某个数字强行铺满外接矩形；
- 连续三页不得都是“左侧标题 + 右侧漂浮卡片”；
- 标题 / 正文与主视觉必须有独立空间，禁止正文从卡片或主体后面穿出；
- 页面上每一个 orb、光晕、渐变和玻璃层都要回答“它解释了什么”；回答不了就删除；
- 同一页超过 4 个模块时，优先改成共享底板、色带、拼贴或内容板，避免 4 个同权重白卡；
- “丰富”页面中的每个模块至少具备一个标签 + 一条具体内容 + 一个视觉证据中的两项；伪线条、空白占位框和随机图标不计为内容；
- 每页先确定一个 `visual subject`，再安排文字；不要先把标题和正文排完，再找装饰物填空。

#### 70–70 页面密度原则

本 skill 默认采用用户提出的 70–70 原则：至少 70% 的页面保留至少 70% 的留白；用主要内容外接矩形表示“占据体积”时，这等价于至少 70% 的页面满足 `envelopeCoverage <= 0.30`。剩余页面才允许作为内容板、生态总览或满版视觉峰值。对 8 页 deck，至少 6 页必须达到这个阈值。

这里的“覆盖率”不计算元素自身填充了多少像素，也不把背景色、流动渐变、页码和控制条算进去。它计算的是标题、正文和主视觉组共同形成的最小轴对齐外接矩形：元素之间的空隙也属于这个外围体积，元素散得越开，覆盖率越高。这正是用来判断“画面是否占得太满”的量。

计算方法固定为：在动效完成、页面停稳的 1920×1080 画面中，取 `headline`、`supportingCopy`、`primaryVisualGroup` 的联合边界；设外接矩形宽高为 `W_box`、`H_box`，舞台宽高为 `W_stage`、`H_stage`，则 `envelopeCoverage = (W_box × H_box) / (W_stage × H_stage)`，`whitespaceCoverage = 1 - envelopeCoverage`。`eyebrow`、caption、控制条、背景效果不计入。为每个 scene 写入 `contentBounds` 和由它推导出的 `coverageTarget`，并在 HTML / PPT 预览中复核：

```json
{
  "densityRule": {
    "name": "70-70",
    "metric": "primary-content-envelope",
    "boundingBox": "axis-aligned",
    "maxContentCoverage": 0.3,
    "minimumPagesUnderMax": 6,
    "include": ["headline", "supportingCopy", "primaryVisualGroup"],
    "exclude": ["eyebrow", "caption", "controls", "backgroundEffects"]
  },
  "slides": [
    {"id": "hero", "coverageTarget": 0.711, "contentBounds": {"x": 0.06, "y": 0.11, "w": 0.90, "h": 0.79}, "visualMode": "hero"},
    {"id": "summary", "coverageTarget": 0.583, "contentBounds": {"x": 0.06, "y": 0.24, "w": 0.87, "h": 0.67}, "visualMode": "rich-board"}
  ]
}
```

执行规则：

- 低密度页优先使用一个视觉主语、一个标题和一条 supporting line；
- 低密度页的主要内容外接矩形通常控制在 15–30%，让页面真正保留至少 70% 留白；主视觉本身可以更小，不要用大范围容器或默认文本框把它撑满；
- 低密度页额外设置空间预算：至少保留一个连续的、没有主要内容的安静区域，面积目标不低于画面的 25%；主要可见元素控制在 3 组以内；
- 标题、正文、主视觉和底部说明必须有独立边界。1920×1080 预览中，主视觉顶部至少与正文底部相距 24 px；若距离不足，先缩小或下移主视觉，不要把正文压进卡片之间；
- 感到“太满”时按此顺序删减：装饰光晕 → 次要标签 → 多余边框/玻璃层 → 重复卡片；不要先缩小正文来掩盖结构问题；
- 高密度页可以超过 40%，但必须有明确主题、中心层级和内部关系，不能只是把小卡片铺满；
- `coverageTarget` 不能凭感觉填写：先测 `contentBounds`，再用 `w × h` 推导；只改透明度、阴影或背景，不会降低外接矩形覆盖率；
- 如果元素之间的空白很大但外接矩形仍然很大，优先收拢布局或缩小视觉组；如果单个共享底板内部内容丰富，则允许它成为高信息密度页，但仍要记录真实外接矩形；
- 如果 8 页中少于 6 页满足 `coverageTarget <= 0.3`，优先缩短文本框、收拢组件或拆页，不通过换背景和降低透明度来“伪装简约”；
- 如果一个页面同时有标题、正文、四个卡片、装饰 orb 和底部说明，先删除装饰层，再判断是否需要拆页；
- 一页的元素少，不代表画面要空；通过主体尺度、留白和单一颜色锚点制造发布会感。

#### 隐藏矩形冲突检查

每一个独立排版元素都必须先生成一个不参与布局的隐藏外接矩形，再进行相交检测；不要只靠肉眼判断或依赖透明度掩盖冲突。

- HTML / Remotion：给 eyebrow、headline、supporting copy、primary visual、caption 和独立 CTA 标记 `data-collision-id`，用 `getBoundingClientRect()` 或文字 Range 的紧包围矩形生成 probe；默认隐藏，`?collision-debug=1` 时显示；
- PowerPoint / Keynote：给每个独立元素在同一坐标上放置 100% 透明的矩形 probe，并在生成阶段对矩形坐标执行 pairwise intersection；按钮里的文字、图标、圆形底座也要作为同层 peer 单独检查，不能因为它们都属于“按钮”就跳过；
- 文本用文字 ink bounds，容器 / 图片 / 卡片用 box bounds；主视觉内部的嵌套内容不与自己的父组比较，但组内彼此独立的主体必须单独标记。若父组和子元素同时存在，比较“父组 vs 外部元素”以及“子元素 vs 同组 peer”，不比较“父组 vs 自己的子元素”；
- 矩形相交即失败，即使视觉上只被阴影、渐变或半透明层“软化”；子 probe 超出其声明的父 probe 也失败；只有明确的嵌套关系可以豁免父子相交，不能豁免子元素越界；
- 每次改字号、换行、位置、容器尺寸或动效终点后，都要按页面顺序从第 1 页跑到最后一页；不能只审最后一页。HTML 实现应提供全页审计入口，在每页停稳后记录 `pass / fail`、相交元素名称、父框越界和停稳时间点。若出现文字被图标盖住、标签被圆形按钮裁掉等问题，优先修正 probe 相交，而不是用透明度、z-index 或阴影遮掩。

颜色的推导顺序：

```text
事件主视觉 → 背景明度 → 文字对比 → 一个强调色
→ 产品 / UI 自带色 → 语义色（只在必要时）
```

#### 字体与文字

优先使用本机可用、拥有授权的系统类无衬线字体。英文可使用 `-apple-system, BlinkMacSystemFont, "Helvetica Neue", Arial`；中文可使用 `PingFang SC`, `Hiragino Sans GB`, `Noto Sans CJK SC`, `Microsoft YaHei`, sans-serif。不要默认打包或分发 Apple 私有字体。

1920×1080 的起始规格：

| 角色 | 尺寸 | 字重 | 行高 |
| --- | ---: | ---: | ---: |
| Eyebrow | 26–32 px | 600 | 1.1 |
| Main headline | 84–148 px | 600–700 | 0.95–1.05 |
| Supporting line | 44–64 px | 400–500 | 1.1–1.2 |
| Body / label | 30–44 px | 400–500 | 1.2–1.35 |
| Caption / footnote | 22–28 px | 400 | 1.25 |

执行规则：

- 标题通常不超过 12 个词；中文通常不超过两行；
- 优先通过删字、拆 scene、改变换行解决拥挤，不要把标题缩小到难读；
- 使用 Regular / Medium / Semibold / Bold，避免小字号 Thin / Ultralight；
- 用字号、字重、位置和留白建立层级，少用描边、渐变字或阴影；
- 数字需要和单位、时间范围、样本口径或来源紧邻；
- 中文要特别检查标点挤压、数字与中文间距、英文品牌名断行和行末孤字。

### 5. 用材质和图像解释概念

苹果式质感的重点不是“玻璃滤镜”，而是让材料与主张相关：

- 产品：用轮廓、侧面厚度、接口、边缘高光和受控倒影证明形体；
- 软件：用真实 UI 状态、前后状态、手势路径和设备之间的关系证明体验；
- 性能：用单一大数字、可理解的对比或视觉化尺度，不要堆规格表；
- 创作：用手、笔、纸张、颜色、材料或工作台，把抽象工具变成可感知动作；
- AI：先展示用户意图和结果，再用少量流程解释系统如何完成；
- 空间 / 影像：用层叠、遮挡、景深、柔和阴影和稳定锚点建立空间关系。

图像原则：

- 一页优先一个主体：一张主图、一个设备、一张 UI 或一个图形；
- 让图像比文字多回答一个问题，否则它只是装饰；
- 保持产品纵横比，只有在构图需要时才裁切；
- 背景渐变、光晕、景深、阴影都要服务于焦点；
- 需要给图片上的文字加底时，优先使用真实对比、局部暗化或明确的容器；
- 不用“多张小图 + 多张卡片”模拟信息丰富度。

### 6. 设计 reveal 和动效节奏

默认时间线：

```text
0.00–0.25  留出舞台 / 背景稳定
0.25–0.70  eyebrow 或短标签出现
0.55–1.20  标题轻微淡入 / 上移
0.90–1.60  主体、数字或产品进入
1.60–      留出阅读和情绪停顿
```

动效规则：

- 先标签、再主张、后视觉证据；层级顺序本身就是讲解顺序；
- 常规入口使用 0.35–0.70 秒的 easing window；
- 使用淡入、短位移、遮罩 reveal、轻微 scale、crossfade 或有方向的 slide；
- scale 必须有稳定锚点，不能让产品像弹簧一样跳；
- wipes、flips、camera spin 只在内容确实发生结构切换时使用；
- 每次 reveal 后保留阅读停顿，不能把关键信息藏进快动作；
- HTML 可以用 CSS 做预览，但需要视频输出时，所有关键运动改为帧驱动；
- 30 fps 下采用 `useCurrentFrame()`、`interpolate()`、无回弹 spring 或 bezier easing；
- `prefers-reduced-motion` 时移除 scale / translation，只保留即时状态或 opacity-only 过渡。

发布会感的关键不是动效多，而是“上一状态为什么会变成下一状态”一眼可懂。

动效验收再加一条：暂停在进入和离开的中间帧，主体、文字和路径仍应构成可理解的画面。如果中间帧只是模糊、漂浮或叠影，说明转场没有 anchor，应改为干净 cut、mask-reveal 或沿边缘的 morph。

### 7. 选择实现方式

#### Keynote / PowerPoint

- 先建立母版：背景、标题线、字号角色、页脚和安全边距固定；
- 每个 scene 类型做一个母版，而不是每页手工自由排版；
- 使用 Magic Move / Morph 只承担对象连续性，不承担复杂特效；
- 用遮罩、分组、层级和路径实现产品揭示；
- 所有数据保留可编辑源，同时在备注或脚注中保留来源；
- 导出前检查嵌入字体、视频编码、换行、透明度和低配置设备播放。

#### Figma

- 将 `Stage`, `Title`, `ProductHero`, `FeatureCallout`, `Stat`, `DemoFrame`, `Chapter` 做成组件；
- 用变量管理背景、文字、强调色、间距和字号；
- 用 variants 管理 dark / light、image-left / image-right、with-caption / no-caption；
- 用 Smart Animate 预览连续性，但最终视频不要依赖无法控制的实时插值；
- 组件只解决重复结构，不要把每页都强行塞进同一个卡片组件。

#### HTML / Remotion

- 用 JSON 做内容真源：文字、scene 类型、时长、过渡、图片说明、speaker note 分开；
- 固定 1920×1080 stage，再按容器缩放，避免不同 viewport 改变构图；
- 每个 scene 一个组件，先用静态画面验收，再加入动效；
- Remotion 使用帧驱动的 `useCurrentFrame()` + `interpolate()`；
- 预览必须支持键盘前后翻页、播放 / 暂停、进度、无障碍标签和自动推进；
- 有旁白或音乐时提供 captions / transcript；静音播放也必须保留核心意义。

## 发布会式 scene 处方

### 处方 A：黑场产品 reveal

```text
黑场 → 极短 eyebrow → 产品轮廓 / 侧面高光 → 名称 → 一句承诺
```

只展示一个角度；如果产品很薄，就让侧面成为主角；如果卖点是材质，就让光线沿边缘移动。不要同时显示全家族、规格和价格。

### 处方 B：软件体验 reveal

```text
熟悉的摩擦 → 一句新的体验 → UI 由模糊到清晰 → 真实动作 → 结果
```

不要先放一整张 UI 让观众找重点。先显示用户任务，再用局部放大、手势轨迹或前后状态把“少了一步什么”说清楚。

### 处方 C：性能证明

```text
一个问题 → 一个数字 / 对比 → 视觉化规模 → 限定条件 / 来源
```

把数字作为主视觉；正文只解释口径。若数字无法验证，改成定性表达或明确标注“示例 / 目标 / 估算”。

### 处方 D：生活化 demo

```text
人物正在做的事 → 设备进入场景 → 1–3 个动作 → 结果改变了什么
```

场景不是素材堆砌。每个镜头都回答“这个功能让谁的哪一步变轻松”。

### 处方 E：章节转场

```text
上一段的关键形态 / 颜色 → 变形或交叉淡化 → 章节名 → 下一段的主色 / 主体
```

转场要让观众感到故事仍在同一条轨道上；颜色变化和形态变化至少保留一个连续性。

## 质量验收

在交付前按 100 分检查：

| 维度 | 分值 | 通过标准 |
| --- | ---: | --- |
| 叙事 | 25 | 有明确承诺；每页一个主张；顺序服务于听众而非资料来源 |
| 层级 | 20 | 3 秒找到标题与主视觉；标题是结论而非目录 |
| 系统 | 20 | 栅格、字号、颜色语义、重复组件和页脚稳定 |
| 视觉 | 15 | 每个视觉都解释或证明内容；没有装饰性卡片墙 |
| 动效 | 10 | 入口有层级；转场有理由；每个 reveal 有阅读停顿 |
| 可访问性 | 10 | 对比度、字号、字幕、非颜色提示和 reduced motion 完整 |

任何一项低于该项总分的 60%，都不能只做微调。优先重构结构，再重做视觉系统。

以下情况直接判定为结构不通过，不进入配色微调：

- 标题或正文被主视觉遮挡、穿插或压在不可读区域；
- 连续 3 页构图轮廓相同，只有颜色变化；
- 页面有 4 个以上同权重模块，但没有共享主题或中心层级；
- 视觉主元素不能在 3 秒内说明“它是什么 / 代表什么动作”；
- 动效暂停在中间帧时无法解释元素的来源和去向；
- 总结页只有栏目名，没有具体内容、证据或关系。

### 交付检查清单

- [ ] 画布比例正确，关键元素在安全区内；
- [ ] 标题在缩略图和现场远距离都能读；
- [ ] 中文没有意外断行、孤字和标点挤压；
- [ ] 每页只有一个视觉中心；
- [ ] 颜色在深色和浅色背景下都有足够对比；
- [ ] 不用颜色作为唯一状态信号；
- [ ] 每个数字有单位、时间、口径和来源；
- [ ] 图片没有无意裁切，设备比例没有变形；
- [ ] 动效在静音状态下仍然传达重点；
- [ ] reduced-motion / captions / transcript 已验证；
- [ ] 没有未经授权的 Apple 标志、截图、产品图、视频、音乐或私有字体；
- [ ] 最终源文件可编辑，导出文件可播放，备注和来源仍存在。

## 最小调用模板

当你要把一份内容交给这套 Skill 时，先输出：

```text
1. 一句话 promise
2. 8–12 个 scene 的标题与主张
3. 每个 scene 的类型、主视觉、证据、时长
4. 16:9 版式令牌与颜色关系
5. reveal / transition / reduced-motion 方案
6. 资产许可和来源清单
7. 逐页 QA 结果与待修项
```

最终目标：不是让任何 deck 看起来都像黑底的 Apple 海报，而是让听众像看一场好的产品发布会一样，知道下一秒为什么出现这个画面、这个画面为什么重要，以及自己应该记住什么。
