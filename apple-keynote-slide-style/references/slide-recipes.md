# Slide recipes

这些 recipe 把事件观察转成可执行的布局。它们描述“关系”和“节奏”，不是 Apple 的原始页面，也不要求使用 Apple 品牌资产。

## 统一 stage

```text
1920 × 1080
左右安全边距：80 px
上下安全边距：100 px
12 列栅格
列间距：24 px
基础间距：8 px
```

建议在设计文件中建立四条共享导线：

```text
headline-baseline  所有主标题的共同基线
subject-axis       产品 / UI / 人物的主轴
detail-line        supporting text、规格或来源的起始线
footer-line        章节标记、日期、来源或页码
```

## 01 / Hero statement

适合开场、章节第一句话、结尾。

```text
┌──────────────────────────────────────────────┐
│ eyebrow                                      │
│                                              │
│                ONE CLEAR                     │
│                PROMISE                       │
│                                              │
│              short support                   │
└──────────────────────────────────────────────┘
```

规则：

- 标题尽量是一句结论，不是“产品介绍”；
- 画面只保留一个视觉锚点，可以是抽象形态、照片或一项巨大数字；
- 事件色可集中在标题关键词或背景边缘，不要整页撒满渐变；
- 开场至少留出一段没有信息增量的停顿，让观众进入舞台。

## 02 / Product reveal

适合硬件、核心模块、产品命名或第一次出现的概念。

```text
┌──────────────────────────────────────────────┐
│ eyebrow                   product name       │
│                                              │
│  title                         ◯              │
│  one-line claim             product           │
│                             silhouette        │
│                                              │
└──────────────────────────────────────────────┘
```

三种常用构图：

1. 居中轮廓：适合“这是它”的第一次揭示；
2. 右侧产品 + 左侧标题：适合产品形态需要留出说明空间；
3. 巨大局部裁切：适合材质、接口、镜头、纹理或边缘厚度。

动画：从黑场或事件色中淡出，先出现轮廓，再出现名称，最后出现一项可验证的差异点。避免一次性展示产品全家族和所有规格。

## 03 / Feature close-up

适合一个功能、一个交互或一个材料特征。

```text
┌──────────────────────────────────────────────┐
│ short title                                  │
│                                              │
│  one visual / one UI state                    │
│                                              │
│                         benefit in one line  │
└──────────────────────────────────────────────┘
```

内容公式：

```text
动作或问题 → 功能出现 → 用户得到的结果
```

不要从一张完整 UI 截图开始。先突出用户正在做的事，再放大关键区域，最后回到完整场景证明它确实能工作。

## 04 / Lived demo

适合把抽象功能变成生活、工作或创作体验。

```text
┌──────────────────────────────────────────────┐
│ scene title                                  │
│                                              │
│       person / workspace / device            │
│                                              │
│  step 1  →  step 2  →  outcome               │
└──────────────────────────────────────────────┘
```

最多保留 3 个动作：

- 用户有一个明确意图；
- 产品或软件减少一个阻力；
- 结果在画面中可见。

如果 demo 需要讲 5 个以上步骤，把它拆成“体验预告”和“细节解释”两段，而不是把所有步骤压到一页。

## 05 / Stat / proof

适合性能、规模、速度、续航、重量、厚度、覆盖范围等可验证指标。

```text
┌──────────────────────────────────────────────┐
│ proof label                                  │
│                                              │
│                    3×                        │
│             faster at ______                 │
│                                              │
│ source · time · method · footnote            │
└──────────────────────────────────────────────┘
```

规则：

- 一个 scene 只放一个主数字；
- 单位紧邻数字；
- 口径、时间范围、样本或测试条件放在脚注；
- 如果是目标、估算或示例，直接标明，不要伪装成事实；
- 颜色只强调方向，数字和文字必须独立可读。

## 06 / Comparison

适合 before / after、上一代 / 新一代、手动 / 自动、输入 / 输出。

```text
┌──────────────────────────────────────────────┐
│ comparison claim                              │
│                                              │
│  BEFORE                  AFTER                │
│  one state               one state            │
│                                              │
│  label                   label                │
└──────────────────────────────────────────────┘
```

先写比较结论，再决定左右顺序。比较的差异不超过 3 个维度；如果每个维度都需要长句，拆成多页。

## 07 / Platform system

适合多产品、多版本、多平台或跨设备能力。

```text
┌──────────────────────────────────────────────┐
│ system promise                               │
│                                              │
│  platform A ─────┐                           │
│  platform B ─────┼── one shared behavior     │
│  platform C ─────┘                           │
│                                              │
└──────────────────────────────────────────────┘
```

先讲跨平台的共同体验，再分别进入产品细节。不要用 8 个 logo 组成“目录页”代替真正的系统关系。

## 08 / Availability / close

适合价格、发布日期、版本、CTA、下一步。

```text
┌──────────────────────────────────────────────┐
│ one-line conclusion                          │
│                                              │
│                available                     │
│              September 20                    │
│                                              │
│                 CTA                          │
└──────────────────────────────────────────────┘
```

把价格和可用性放在观众已经理解价值之后。结尾重复承诺，不再打开新功能；如果需要列条款，放到附录或单独的安静信息页。

## 09 / Rich content board

适合总结页、平台能力、生态关系和“一个主题包含多个结果”的页面。

```text
┌──────────────────────────────────────────────┐
│ board title                         short note│
│                                              │
│  ┌──────────────┐  ┌──────────────┐          │
│  │ topic + fact │  │ topic + fact │          │
│  ├──────────────┤  ├──────────────┤          │
│  │ topic + fact │  │ topic + fact │          │
│  └──────────────┘  └──────────────┘          │
│ source / path / next action                   │
└──────────────────────────────────────────────┘
```

规则：

- 先定义 board 的中心主题，再决定模块数量；
- 每个模块至少有标签、具体内容、视觉证据中的两项；
- 模块属于同一共享底板，避免四张互不相干的白卡漂浮在舞台上；
- 中心主题或标题占 40–55% 的视觉权重，边缘模块负责补充语境；
- 可以使用色块、分隔线、裁切图、数字或 UI 状态，但不能用伪线条填空；
- 内容板不是把所有东西都缩小，而是让信息形成一个可扫读的关系图。

## 10 / Full-bleed visual peak

适合产品家族、创作场景、材料、空间或一次情绪性的视觉记忆点。

```text
┌──────────────────────────────────────────────┐
│                                              │
│           one full-bleed subject             │
│                                              │
│  short label                                  │
└──────────────────────────────────────────────┘
```

规则：

- 主体占 80% 以上画面，可以出血和裁切；
- 文字退到一个短标签或一句结论；
- 不在满版视觉上再叠一整套卡片、按钮和说明；
- 前后场景至少共享一个颜色、边缘、动作或主体，保证转场不是随机换图；
- 如果没有真实 / 授权图片，使用一个原创的大形态或内容板，不要用小图标拼成“假满版”。

## 颜色换肤表

使用同一 scene 骨架切换不同事件皮肤：

| 皮肤 | 背景 | 文字 | 强调 | 材质语言 | 适用内容 |
| --- | --- | --- | --- | --- | --- |
| Night / hardware | `#000000` | `#F5F5F7` | 冷蓝或暖橙 | 金属、边缘光、软阴影 | 产品、性能、结构 |
| Soft light / creative | `#F5F5F7` | `#111113` | 粉、黄、蓝中的一个 | 纸张、笔触、柔和浮影 | 创作、教育、工具 |
| Iris / software | 深灰或近黑 | 白 | 虹彩渐变 | 流动、发光、空间层 | AI、系统、沉浸 |
| Clean system | `#FFFFFF` | `#1D1D1F` | 蓝或系统色 | 轻层级、少阴影 | 平台、规范、可信度 |

事件色只换皮肤，不换层级。只要标题、主视觉和阅读顺序仍然成立，颜色才算系统的一部分，而不是装饰。

## Keynote 构建顺序

1. 建 1920×1080 母版和安全区；
2. 建 title / statement / reveal / demo / proof / close 六类母版；
3. 用灰度填入所有内容，先验收故事和比例；
4. 为每个章节分配一个主视觉和一个强调色；
5. 引入真实或授权资产，检查裁切、比例和对比；
6. 加入 build order：标签 → 标题 → 视觉 → 证据；
7. 逐页加备注、来源、字幕或 transcript；
8. 以完整尺寸和全稿缩略图各检查一次；
9. 只在结构稳定后加入质感、光晕和转场。

## PowerPoint 构建顺序

使用 Morph 维持对象连续性，使用透明 PNG、裁切和基础路径做 reveal；保持动画少且可预测。不要为了模拟片中镜头而加入过多镜头旋转、翻页、弹跳或 3D 翻转。

## HTML / Remotion 构建顺序

- 每个 scene 变成独立组件；
- 用统一 `Stage` 控制比例和安全区；
- 用 `durationSec` 计算整数帧；
- 用 `useCurrentFrame()` 和 `interpolate()` 控制所有关键运动；
- 在 scene JSON 中保存 `alt`, `caption`, `speakerNote`, `license`；
- 先渲染 still，再渲染一段完整预览，最后再决定是否输出视频。

## 反例修复

| 反例 | 表面症状 | 修复动作 |
| --- | --- | --- |
| 黑底白字即苹果 | 没有叙事、产品或体验 | 先写 promise 和 lived demo |
| 一页塞完功能 | 字变小、卡片变多 | 拆成 reveal / demo / proof |
| 颜色过量 | 每个模块都在发光 | 只保留一个事件色和必要语义色 |
| 玻璃滤镜滥用 | 背景、卡片、按钮都透明 | 只有确实需要层级和深度时使用材质 |
| 伪数据大数字 | 只写“10× 更快” | 补单位、口径、条件、来源或改成定性描述 |
| 复制 Apple 资产 | 视觉像海报复印件 | 改用自己的形态、色彩和产品资产 |
| 过度动效 | 观众只记得转场 | 将动效绑定到状态变化和讲解顺序 |
| 浅色卡片模板 | 背景变浅但仍像 SaaS 仪表盘 | 删除装饰 orb，给内容建立共享底板和明确主语 |
| 标题穿过主体 | 正文被纸张、产品或卡片遮挡 | 为文字预留独立安全区，或把文字归入主体内部 |
| 每页相同密度 | 连续页面只是换色 | 重新编排空舞台、动作、内容板和满版峰值 |
