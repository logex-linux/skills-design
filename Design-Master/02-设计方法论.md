## 一句话模型

**Taste → System → Prototype → Test → Artifact → Distribution**

先建立有来源的审美输入，再将判断写成设计系统；用 AI 快速做出可运行的原型；通过真实使用和反馈修正；把稳定的判断封装为报告、作品集或 Skill；最后通过公开展示和跨平台分发获得下一轮输入。

## 从语料中抽出的判断基线

这些不是账号原话，而是对 Edge 读取样本和公开仓库的归纳：

- 好设计同时追求 **attention、peace、clarity**：先抓住注意力，再制造片刻的平静，最后让人清楚理解对象是什么。
- 克制必须是可执行的：例如 Mono-color 默认一色，必要时最多加入一个强调色；“少”不是空泛审美，而是限制变量数量。
- 工具的价值在于扩大判断的可执行范围：AI、代码、Figma 和 Skill 都服务于问题定义、构图、节奏和取舍，而不是替代它们。
- 一次成功不等于系统：把重复动作写成 SOP、Design System 或 Skill，再通过真实案例、用户反馈和公开分发修正。
- 作品的可信度来自证据链：参考来源、问题定义、过程取舍、可运行结果和下一轮修改要能被读者复核。

## 八条核心原则

### 1. 先重新定义问题，再决定界面

不要从“我要一个页面/按钮/AI 功能”开始。先问：

- 用户真正想完成的结果是什么？
- 哪些步骤只是旧流程的历史遗留？
- AI 能否直接交付结果，而不是只辅助完成旧步骤？

### 2. 把产品当成系统，而不是一张截图

设计分析的起点是 JTBD、核心循环、对象和关系；界面是系统被看见的一层。至少说明：谁在什么情境下触发什么动作，系统如何反馈，用户为什么回来。

### 3. 把 Context 当成界面的一部分

AI 产品必须显式设计上下文：用户身份、历史状态、当前目标、可用资料、缺失信息、记忆边界和下一步行动。Context 不清楚，AI 再强也会让产品显得失控。

### 4. 把审美从“感觉”拆成语言

参考风格时不复制某个作品，而抽取可迁移属性：

- 色彩：主色、辅助色、对比色、使用比例；
- 字体：字阶、字重、行距、语言混排；
- 空间：留白、密度、对齐、节奏；
- 构图：层级、裁切、网格、视觉重心；
- 材质：纸张、颗粒、网点、透明度、光泽；
- 动效：进入、反馈、转场、速度和缓动；
- 语气：信息密度、标题口吻和交互文案。

### 5. 用显式约束让 AI 稳定执行

把上面的语言写成 Design System，而不是只写“做得高级”。至少包含 tokens、允许/禁止事项、组件规则、示例和质量检查。约束不是为了僵化，而是为了让创意可以被重复调用和比较。

一个好的约束应该能直接回答“少到什么程度”：例如颜色数量、留白比例、字阶层级、纹理强度、裁切方式和何时允许例外。

### 6. 以最小垂直切片验证，而不是一次做完整产品

把大目标切成一个可以从输入走到结果的最小闭环。先让用户真的完成一件事，再扩展功能；每次只改变一个关键变量，并保留预期结果与实际结果。

### 7. 展示判断过程，不只展示最后一张图

好的作品集、产品拆解和设计报告要让读者看到：问题是什么、做了哪些取舍、参考从哪里来、AI 在哪里参与、哪些结果被验证、下一步机会是什么。过程证据能建立信任，也能让别人复用方法。

### 8. 把有效方法变成资产并公开迭代

重复出现的设计判断可以被封装成 Skill、模板、报告或作品集模块。公开 Demo、学习过程和失败案例，带来反馈；反馈反过来更新系统。这是一条“作品—反馈—方法—再作品”的内容飞轮。

### 9. 让生产系统保护判断力

把高摩擦步骤批量化，把低价值重复劳动交给 SOP 或 AI，把必须由人决定的部分留出来。高频输出的目标不是每次都做同样的东西，而是让设计者把时间用在问题、语境、比例、节奏和验收上。

## 标准工作流

### Step 0｜写清 Brief

输出一页 Brief：目标用户、任务/结果、场景、约束、成功信号、非目标、交付形态和时间范围。

### Step 1｜建立参考集

选择 3–6 个与目标相近但不完全相同的参考源。每个参考只记录可迁移属性，不直接复制构图、文案、Logo 或独特排列。

### Step 2｜提炼设计语言

把参考集转换成一份小型视觉系统：palette、type scale、spacing、layout grammar、image treatment、motion grammar、content hierarchy 和 accessibility rules。

### Step 3｜定义 AI-native 协作

明确 AI/Agent 的角色：它负责什么、何时主动、何时等待、何时给建议、哪些决定必须由人做。写出 Context 来源、记忆方式、失败回退和人工接管点。

### Step 4｜做一个最小原型

用 AI Coding 或其他实现工具把一个端到端闭环做出来。先验证“用户能否完成目标”，再处理装饰、扩展页面和边缘功能。

### Step 5｜基于证据评审

至少跑三类检查：

1. 任务检查：目标是否完成？
2. 体验检查：信息层级、延迟、空状态、错误和反馈是否清楚？
3. 系统检查：颜色、字体、间距、组件和动效是否遵守约束？

将每个问题写成“预期 → 实际 → 影响 → 下一次修改”，不要只写审美形容词。

### Step 6｜封装和交付

根据稳定程度选择交付物：视觉系统、产品拆解、作品集案例、单文件 HTML 报告或 Skill。交付物必须包含适用范围、输入方式、质量门槛和已知限制。

### Step 7｜公开反馈与分发

把案例拆成适合不同平台的形式：短帖讲一个判断，长文讲完整流程，作品集放证据，Skill 提供复用入口。记录反馈并回写到系统，而不是只追求一次传播。

## 适用于视觉方向的最小决策表

在生成视觉或界面前，先写下这 8 个决定：

| 决定 | 要回答的问题 |
|---|---|
| 目标 | 用户看到后要理解、决定或完成什么？ |
| 注意力 | 第一眼由什么抓住？ |
| 平静 | 哪些元素必须被删掉，才能留出呼吸？ |
| 清晰 | 层级、字阶和动作是否一眼可读？ |
| 约束 | 颜色、字体、空间、材质和动效的上限是什么？ |
| 语境 | 用户、历史状态和输入资料是什么？ |
| 证据 | 用哪一个最小闭环证明它有效？ |
| 资产 | 这次判断如何变成模板、Skill、报告或作品集案例？ |

## 失败模式与修正

| 失败模式 | 表现 | 修正 |
|---|---|---|
| 只说“高级感” | AI 生成结果每次都不一样 | 改写为色彩、字阶、留白、构图和材质规则 |
| 先堆功能 | 原型很大但没有完成任何任务 | 砍到一个最小闭环 |
| 复制参考图 | 结果像临摹，缺少自己的问题语境 | 只抽取系统属性，重新构图和写作 |
| 把 AI 当黑箱 | 不知道 AI 何时主动、何时停止 | 设计 Context、控制点和人工接管 |
| 只展示成品 | 无法判断设计者如何做决定 | 展示 Brief、取舍、迭代和验证证据 |
| 方法不能复用 | 每次从零开始提示 | 把稳定判断封装为 Design System 或 Skill |
| 过度追求单一风格 | 所有内容看起来一样 | 保持统一规则，同时允许主题和媒介变化 |

## 完成检查表

- [ ] 问题、用户、场景和非目标写清楚。
- [ ] 设计参考有来源，并已被抽象为属性。
- [ ] 视觉系统至少包含色彩、字体、空间和内容层级。
- [ ] AI/Agent 的 Context、控制点和失败回退已定义。
- [ ] 至少一个最小端到端闭环真实运行过。
- [ ] 评审记录包含预期与实际，而不是只有主观评价。
- [ ] 交付物能被截图、打印、分享或再次调用。
- [ ] 没有复制第三方的独特构图、文案、Logo 或品牌资产。
